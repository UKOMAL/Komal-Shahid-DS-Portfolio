Hybrid RAG, built from scratch for production.

I owned the design and build of an end-to-end retrieval pipeline for enterprise GenAI use cases. The first version worked in the demo and failed silently in the places that mattered.

The failure that started it.

The first iteration used dense-only retrieval. Embed the query, embed the documents, return nearest neighbours. It performed well on every query we demoed.

Then it started missing things. Not dramatically — that would have been easier. It missed exact-term lookups: identifiers, proper nouns, error codes. Terms where the literal string is the whole point and semantic similarity is close to meaningless.

The reason this class of bug is expensive is that nothing looks broken. The retriever returns something, the model reads it, and the answer comes back fluent and confident and wrong. There is no stack trace. Without deliberate evaluation against exact-term queries, it does not surface at all.

The lesson

Dense retrieval doesn't fail loudly. It returns a plausible neighbour and lets the language model paper over the gap.

A note on source code

The production system described here was built at Discover / Capital One and is proprietary — the implementation isn't mine to publish. This page documents the architecture, the failure mode that drove the rebuild, and the reasoning behind each decision. The linked repository holds the architecture write-up plus a runnable reference implementation of the same patterns — BM25 from scratch, Reciprocal Rank Fusion, a labelled evaluation corpus and the compression sweep that shows the failure mechanism.

I'm happy to walk through the implementation in detail in conversation, including the parts that didn't work.

What I rebuilt.

Hybrid retrieval, because the two failure modes are complementary. Dense embeddings miss exact terms; BM25 misses paraphrases. Running both and fusing the rankings covers each one's blind spot.

  1. Ingestion and chunking — documents split with deliberate overlap, tuned against retrieval quality rather than just fitting a token budget.
  2. Parallel retrieval — BM25 lexical search and BGE dense embeddings run against the same corpus, independently.
  3. Reciprocal Rank Fusion — the two ranked lists merge into one. RRF cares about rank position, not raw scores, so it doesn't require the two retrievers to be on a comparable scale.
  4. Cross-encoder reranking — a precision pass over the top-k only. Too expensive for the full corpus, exactly right for a shortlist.
  5. HyDE expansion — for underspecified queries, generate a hypothetical answer first and retrieve against that instead of the sparse original query.
  6. Grounded generation — synthesis with citations, and access control applied at retrieval rather than in the interface.

# Two retrievers, one ranking. RRF works on positions,
# so BM25 scores and cosine similarities never need
# to be normalised onto a common scale.
def reciprocal_rank_fusion(rankings, k=60):
    scores = defaultdict(float)
    for ranking in rankings:
        for pos, doc_id in enumerate(ranking):
            scores[doc_id] += 1.0 / (k + pos + 1)
    return sorted(scores, key=scores.get, reverse=True)


def retrieve(query, top_k=50, rerank_to=8):
    dense  = vector_store.search(embed(query), k=top_k)
    sparse = bm25.search(query, k=top_k)

    fused = reciprocal_rank_fusion([dense, sparse])[:top_k]

    # Precision pass on the shortlist only.
    return cross_encoder.rerank(query, fused)[:rerank_to]
Why top-k first: the cross-encoder scores every query-document pair jointly, which is what makes it accurate and what makes it far too slow to run over a full corpus. Fusion narrows the field; reranking sharpens it.

Built for many use cases.

The requirement was never a single application. It was shared infrastructure that several teams could build on — which changes what counts as a design decision rather than an afterthought.

ConcernHow it was handled
Access controlEnforced at retrieval. Documents are filtered by the caller's permissions before they ever reach the model. Filtering in the interface is a data leak waiting to be found.
Re-indexingSource keys retained in metadata. When the embedding model changes, re-chunk and re-embed from the originals — no re-upload, no coordination with every consuming team.
EvaluationRetrieval quality instrumented from the start, including an exact-term query set built specifically because of the original failure.
Multi-tenancyIsolation at the retrieval layer, so use cases share compute without sharing corpora.
What I'd tell a customer

If your RAG system has never been evaluated on queries where the exact string matters, you don't yet know whether it works.
