The container doesn't ship the driver.

The most common GPU deployment failure: someone builds a CUDA image, runs it on a GPU instance, and torch.cuda.is_available() returns False. The image carries the CUDA runtime; the host carries the driver. If the host driver is older than the runtime the image expects, nothing works — and the error message rarely says so.

  1. nvidia-smi on the host — is the driver installed and healthy? If this fails, nothing else matters.
  2. NVIDIA Container Toolkit installed? Without it, Docker has no way to expose the device.
  3. Started with --gpus all? Absent that flag the GPU is simply not passed through.
  4. docker exec <cid> nvidia-smi — if the container sees the device but PyTorch doesn't, it's the framework build.
  5. Wheel CUDA-matched? A cu121 torch build on a driver too old for CUDA 12.1 fails exactly this way.
Dockerfile · GPU inference imageCUDA 12.1
# Runtime lives in the image. Driver lives on the host.
FROM nvidia/cuda:12.1.0-runtime-ubuntu22.04

ENV DEBIAN_FRONTEND=noninteractive PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y --no-install-recommends \
      python3.10 python3-pip && rm -rf /var/lib/apt/lists/*

# cu121 wheels must match the base image CUDA line.
RUN pip3 install --no-cache-dir torch==2.3.0 \
      --index-url https://download.pytorch.org/whl/cu121

# Bake weights in or mount them — never download on cold start.
COPY app/ /app/
WORKDIR /app

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python3 -c "import torch,sys; sys.exit(0 if torch.cuda.is_available() else 1)"

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]
Host side: install nvidia-container-toolkit, then docker run --gpus all -p 8080:8080 rag-svc:latest. On AWS a Deep Learning AMI ships driver and toolkit preinstalled, removing the whole class of problem.
Why it matters

Anyone can write a Dockerfile. Knowing which layer owns the driver is what separates having deployed this from having read about it.

Right-size the box before you optimise the model.

Customers routinely overspend by an order of magnitude because someone picked a training instance for an inference workload. The question isn't which GPU is fastest — it's whether the model fits in VRAM, and whether the workload is latency-bound or throughput-bound.

InstanceReach for it when
g4dn.xlarge
T4 · 16GB		Cheapest real GPU. Inference for smaller or quantized models, embedding generation, batch reranking. My default start for a RAG serving tier.
g5.xlarge
A10G · 24GB		The sensible middle. Roughly 2–3× the T4 on transformer inference for a modest premium. Where most production inference should land.
p3 / p4d
V100 / A100		Training and full fine-tunes. Justify with utilization, not ambition. Spot plus checkpointing makes it affordable.
c6i / m6i
CPU only		More viable than people assume. My LoRA fine-tune ran CPU-only. BM25, chunking, and orchestration never need a GPU.

SageMaker or raw EC2

SageMaker when the customer wants managed training jobs, endpoint autoscaling, and has no infrastructure team — you pay a premium for not operating it. Raw EC2 when they need container control, specific CUDA builds, or are cost-sensitive at scale. Both are defensible; pretending only one exists is not.

Deploy · ECR → EC2 GPU hostbash
# 1 — build and push to ECR
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin $ACCT.dkr.ecr.us-east-1.amazonaws.com
docker build -t rag-svc:$SHA .
docker push $ACCT.dkr.ecr.us-east-1.amazonaws.com/rag-svc:$SHA

# 2 — on the GPU host
nvidia-smi                     # confirm driver before anything else
docker run -d --restart=always --gpus all --shm-size=1g -p 8080:8080 \
  -e AWS_REGION=us-east-1 \
  $ACCT.dkr.ecr.us-east-1.amazonaws.com/rag-svc:$SHA

# 3 — the check that actually matters
docker exec -it $CID python3 -c "import torch; print(torch.cuda.get_device_name(0))"
Instance role, not keys. The container reads credentials from the EC2 instance profile via IMDS. No AWS_SECRET_ACCESS_KEY in an env var — that's the finding every customer security review opens with.

Send the file, or send the pointer?

This comes up on nearly every integration call, and the answer is almost always: send the pointer. Push bytes through your API and you inherit request size limits, timeouts on slow client connections, retry storms that re-upload the whole payload, and memory pressure on a service that should be stateless.

The pattern that scales: the client requests a presigned PUT URL, uploads straight to S3, then calls your API with just the object key. The API moves metadata; S3 moves bytes.

SituationCall it
Under ~1 MB, syncInline in the API. Adding S3 here is complexity with no payoff.
Large files, batchS3 + presigned URL. PDFs, audio, image sets — anything uploaded from a laptop on hotel wifi.
Regulated dataS3 with SSE-KMS. Customer-managed key, bucket policy denying unencrypted PUT, access logged.
Results that persistS3 + short-lived presigned GET. Return an expiring URL, not a blob.
Ingestion · presigned upload flowpython
import boto3, uuid
s3 = boto3.client("s3")

def issue_upload_url(tenant: str, filename: str):
    key = f"raw/{tenant}/{uuid.uuid4()}/{filename}"
    url = s3.generate_presigned_url(
        "put_object",
        Params={
            "Bucket": BUCKET, "Key": key,
            "ServerSideEncryption": "aws:kms",
            "SSEKMSKeyId": CUSTOMER_KMS_KEY,
        },
        ExpiresIn=900,          # 15 min, not 7 days
    )
    # API returns the pointer. Bytes never touch this process.
    return {"upload_url": url, "key": key}


def ingest(key: str):

Why the key lives in metadata: when the embedding model changes — and it will — re-embed from the S3 original instead of asking every customer to upload their corpus again.
